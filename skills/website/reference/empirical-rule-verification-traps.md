# "N cases confirm the rule" — count distinct values before believing it, and check who wrote the fixture

Claiming "formula X reproduces N historical rows to the peso/cent" feels like strong
evidence and can prove nothing at all. Two separate defects look identical to evidence.

## 1. N rows are not N observations

A dataset had 193 sales rows, but only **six distinct prices** and **twelve distinct
price→result pairs**. "157 matching cases" was six numbers repeated 157 times — the real
sample size was 6, and the gap between those two numbers is the entire strength of the
claim.

The check costs one line, and belongs BEFORE citing any count:

```js
new Set(rows.map(r => `${r.input}|${r.output}`)).size   // 6, or 157?
```

Rule: when reporting "the rule holds in N cases," also report **how many distinct input
values** those N cases represent. If the second number is small, that's the one that
matters — say how many, not the row count.

## 2. Measuring against a fixture your own system generated is circular

Worse than the above: if the file being measured against was generated by your own code,
using a rule already shaped like the one being "confirmed," a perfect match is guaranteed
by construction, not evidence of anything external. The values inside it were themselves
invented at an earlier stage, and can be silently wrong.

**The signature: the match is too clean.** Six-for-six, zero dispersion, on real-world
data that should carry noise. When an empirical rule fits with zero residual, the first
hypothesis isn't "great rule" — it's "I'm measuring my own hand."

Questions that catch it before it ships:

- Who wrote the file being measured against? "We did," or "a generator in this repo,"
  means it is not evidence of anything external.
- Do the identifiers/values in that fixture exist in the real source of truth? (Measured
  case: 0 of 6 ids existed in the client-provided document.) That single cross-check would
  have caught it.
- What is the one data point NOT under your control? That's the actual argument; everything
  else is illustration.

## 3. A verifier that respects its own seeding data verifies nothing

A seed script's guard was "respect anything already marked `real`" — and its own previous
run had marked its seeded rows `real`. Running it twice in a row and diffing surfaced it:
the second run reported the same "N respected" whether or not a genuinely new external
list existed to compare against, because the system could not tell its own writes apart
from an outside source.

**Run a verifier or seeder twice in a row, unchanged, before trusting it.** If the second
run differs — or fails to differ when it should — the instrument is the suspect, not the
data.

## What to do on discovery

The conclusion can still be correct even after the evidence for it collapses — fix the
evidence anyway. If a defensible number exists elsewhere (an independent source, even a
single external observation), that's what the claim should cite going forward; what
changes is where it's defended, in the doc, in code comments, in any arbitration message,
not necessarily the number itself. Correct it even when the result doesn't change: the day
someone audits where a number came from and finds it was "measured" against
self-generated data, everything else measured the same way loses credibility too — a
correct number with rotten evidence gets discarded exactly like an incorrect one.

The root cause common to all three cases: **the system couldn't distinguish its own
writes from an external source.** A tighter filter doesn't fix that — recording provenance
(where a value came from) does.
